# Review supplied career outcomes

Apply the manifest gate and sharing disclosure in the
[shared writing method](../../references/writing.md) before processing events.
Only `selected_text_standalone_v1` permits this workflow under the
[standalone boundary](../../references/standalone-profile.md). Obtain explicit agreement;
reuse it in this conversation until revoked or scope changes. Denial stops processing.

## Learn without inventing the campaign

Use only deliberately supplied events, dates, observations and results for the requested
period. Draft files, intended actions and preparation are not evidence of submission,
contact, interviews or offers. Silence after a date is not automatically a rejection or
"no response" outcome. Confirmed-in-chat events remain user-supplied, not independently verified.

1. Separate completed/confirmed events, planned actions, pending statuses and uncertain
   recollections. Preserve exact role/event associations and dates; do not merge similar
   employer names into one event or silently deduplicate unclear repeats.
2. Build a compact chronology or status summary. Identify missing period boundaries,
   duplicates and contradictory accounts that change counts. A user correction replaces
   only the affected event in this conversation, not a stored pipeline record.
3. Describe patterns at the sample's actual size. If counts are clear, state numerators and
   denominators and compute only compatible rates. Avoid conversion rates when cohorts,
   maturity or statuses are incomplete; a small sample cannot establish a causal trend.
4. Separate employer-stated feedback, recruiter summary, user observation and model
   hypothesis. A rejection without a reason does not prove a skills gap. Strong interview
   feelings do not prove employer approval. Do not present hypotheses as employer intent.
5. Recommend a small next-step plan based on the evidence: clarify an unresolved term,
   improve one supported story, reassess a target family or prepare a requested follow-up.
   Explain what observation would test each hypothesis. Suggest a review point without
   scheduling it or creating ongoing monitoring.

## Deliver the review

Return the supplied event/status summary, factual observations with sample limits, separately
labeled hypotheses, and a practical action plan. For each action name its purpose, necessary
input and suggested timing if useful; distinguish suggested dates from existing commitments.
Include the few missing facts that would change the plan. Do not give the user an empty
ledger or generic advice when concrete events support a more useful response.

No event confirmation tool, submission, message, calendar action, score change or pipeline
persistence. If requested, deliver a new local Markdown review with exact readback, never
overwrite a pipeline. A later session requires selected events and fresh sharing agreement.

The [outcome example](../../examples/standalone-workflows.md#outcomes) keeps an unsent draft
out of counts and separates stated feedback from a hypothesis. Stop at review and next steps.
